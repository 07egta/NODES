## 診断の統合前に決めること

[#20 の CLI](https://github.com/07egta/NODES/blob/4ef925c4153b3cc045213147b68d4d16ca61a8e9/src/bin/nodes-cli.rs) は、`diagnose` 内で `graph_api::evaluate` を直接呼び、個別ノードの評価エラーを含む場合も成功応答を返す。#18 は既存の `checked_evaluate` の失敗規約を保ち、終了コード `1` と `error.diagnostics` を返す。成功・失敗の JSON 構造も異なる。同名コマンドを二重に追加せず、一つの契約を選んで統合する必要がある。

[#20 の診断モジュール](https://github.com/07egta/NODES/blob/4ef925c4153b3cc045213147b68d4d16ca61a8e9/src/graph_diagnostics.rs) には、直接接続された失敗・無効ノード、空出力と正常出力の区別、依存深さ、直接の分岐数、実測時間を重みにした依存経路がある。これらは #18 の原因候補、影響先、処理時間 UI を補う候補である。依存経路の時間は全体の実行時間や並列化による短縮量ではない。

注意点: #20 の `parents` / `direct_failed_inputs` は保存された全入力を参照する。クラスタ定義が消費しない静的 `in7` に失敗ノードが接続されている場合、その接続を原因候補として扱う可能性がある。#18 の `real_input_count` による対象制限と未使用クラスタ入力の回帰テストを、統合時の検証に再利用する。

## 作品比較の契約差

[#21 の Python 実装](https://github.com/07egta/NODES/blob/7478fd12fdcd55195e821fd17291351cc7076b25/scripts/project_diff.py) と未公開の Rust 試作は、次の点で交換可能ではない。

| 項目 | #21 の Python ツール | Rust 試作でレビューした契約 |
|---|---|---|
| 対象 | JSON の保存フィールド。スクリプト、クラスタ、未知フィールド、提案中の明示ポート表現も比較 | 現行ネイティブ形式と既存 Graph API の許可範囲 |
| 検証 | 8 MiB 上限、重複 JSON キー、数値の有限性、ID や一部の JSON 構造など | `Project::validate` と `validate_safe` による型・接続・範囲・循環を含む検証 |
| 数値 | 整数・浮動小数点の等価な表記を同一視。`+0.0` と `-0.0` も同一 | パラメータの IEEE-754 ビットを比較し、符号付きゼロを区別 |
| ノード順 | 既存ノードの相対保存順も差分。`--ignore-layout` で除外可能 | 安定 ID で対応付け、保存順だけの変更は無視 |
| 出力 | フィールド単位の全変更リスト | 変更ノード 256 件ずつ。パラメータ・入力詳細は各 64 件、総数と省略フラグあり |
| 影響先 | 評価や依存影響の推定は行わない | 変更後グラフの構造上の潜在的影響先を重複除去して列挙。実際の値変化とは区別 |
| 終了コード | `0` 同一、`1` 差分あり、`2` エラー | 差分の有無にかかわらず比較成功は `0`。作品エラー `1`、使用方法エラー `2` |

Python ツールはネイティブ作品の完全な検証器ではない。Rust 試作は未対応のスクリプト等を実行せず拒否する。どちらも読み取り比較を目的とするが、対応範囲や終了コードを明記せず同じ意味の結果として扱わない。

[#21 のテスト](https://github.com/07egta/NODES/blob/7478fd12fdcd55195e821fd17291351cc7076b25/tests/test_project_diff.py) には確認時点で 10 テストが定義されている。PR 本文の「tests pending」だけで実装状況を判断しない。このレビューでは #20/#21 のテストや CI を実行・検証していない。

## 次回の統合方針

- まず各 PR の最新 head と CI を取り直す。上記 SHA を現在の状態と推測しない。
- 診断は一つの CLI・レポート契約に集約し、既存テストを保って補完的な依存メトリクスを取り込む。
